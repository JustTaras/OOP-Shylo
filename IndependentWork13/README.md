# Самостійна робота №13  
**Тема:** Кейси Polly/Retry: короткий звіт  
**Мета:** Дослідити та проаналізувати реальні сценарії використання бібліотеки Polly для реалізації політик відмовостійкості (Retry, Circuit Breaker, Timeout, Fallback) у .NET-застосунках.

---

## 1. Опис проєкту

Проєкт **IndependentWork13** — це консольний застосунок на C#, у якому реалізовано три сценарії використання бібліотеки **Polly** для підвищення відмовостійкості:

1. Виклик зовнішнього API з тимчасовими помилками (політика **Retry**).
2. Доступ до бази даних, яка періодично "падає" (поєднання **Retry + CircuitBreaker**).
3. Довга операція, яка може перевищити допустимий час виконання (поєднання **Timeout + Fallback**).

Усі сценарії супроводжуються логуванням через `Console.WriteLine`, де видно роботу політик (повторні спроби, перехід станів CircuitBreaker, спрацювання Timeout/Fallback).

---

## 2. Сценарій 1: зовнішній API + Retry

### Проблема

Зовнішні HTTP-сервіси можуть:

- повертати тимчасові помилки (500, 503),
- бути недоступними через короткочасні мережеві збої.

Якщо одразу падати при першій помилці, користувач отримає негативний досвід, хоча проблема могла "зникнути" вже через секунду.

### Обрана політика Polly

- **WaitAndRetry** (3 спроби, зі збільшенням затримки: 1 с, 2 с, 3 с).

**Обґрунтування:**  
Тимчасові помилки часто проходять самі по собі. Кілька повторних спроб з паузою дозволяють успішно завершити операцію без втручання користувача.

### Фрагмент коду

Фрагмент реалізовано в методі `RunScenario1_ExternalApi()` у `Program.cs`.  
Основні моменти:

- перші дві спроби імітують помилку (`Exception`),
- на третій спробі виклик вважається успішним,
- у логах видно номер спроби, час затримки та текст помилки.

### Очікувана поведінка та логи

- 1-ша і 2-га спроби завершуються помилками.
- Polly робить повторні виклики з відповідною затримкою.
- На 3-й спробі виклик успішний.
- У консолі видно приблизно таку послідовність:
  - `[API] Виклик спроба #1...`
  - `[Retry] Спроба #1, затримка 1с. Помилка: ...`
  - `[API] Виклик спроба #2...`
  - `[Retry] Спроба #2, затримка 2с. Помилка: ...`
  - `[API] Виклик спроба #3...`
  - `[API] Успішна відповідь від сервера!`

## 3. Сценарій 2: база даних + CircuitBreaker + Retry

### Проблема

База даних може:

- періодично "впадати" в стан перевантаження,
- повертати таймаути підключення,
- довго не відповідати.

Якщо продовжувати масово надсилати запити в цей момент, ситуація лише погіршується. Потрібен механізм, який **тимчасово заборонить** нові спроби після серії помилок.

### Обрана політика Polly

- **Retry** — 1 додаткова спроба перед тим, як вважати виклик невдалим.
- **CircuitBreaker** — після 2 послідовних помилок переходить у стан **Open** на 5 секунд.

**Обґрунтування:**  

- `Retry` корисний, якщо помилка поодинока.
- `CircuitBreaker` захищає ресурс (БД) від лавинних запитів, коли проблема повторюється.

### Фрагмент коду

Фрагмент реалізовано в методі `RunScenario2_DatabaseWithCircuitBreaker()`:

- перші чотири виклики до БД імітують таймаут (`TimeoutException`);
- після двох помилок поспіль `CircuitBreaker` переходить у стан **Open**;
- наступні виклики одразу кидають `BrokenCircuitException` без реальної спроби звернення до БД;
- у логах видно переходи `Open`, `Half-Open`, `Reset`.

### Очікувана поведінка та логи

- Для перших кількох викликів видно повтори (`[DB-Retry]`) і помилки таймауту.
- Після 2 послідовних помилок:
  - лог `[DB-CB] Перехід у стан Open...`
- Під час стану **Open**:
  - кожен новий виклик викидає `BrokenCircuitException`,
  - у консолі видно повідомлення про заблокований виклик.
- Після закінчення часу `durationOfBreak`:
  - breaker переходить у **Half-Open**,
  - виконується тестовий запит (`onHalfOpen`),
  - при успіху — `onReset` і повернення до нормальної роботи.

## 4. Сценарій 3: довга операція + Timeout + Fallback

### Проблема

Деякі операції можуть:

- виконуватись значно довше очікуваного,
- "зависати" через проблеми сервера або баги.

Якщо не обмежити час, користувач буде довго чекати або взагалі не отримає результату.

### Обрана політика Polly

- **Timeout** — обмеження часу виконання операції (1 секунда).
- **Fallback** — повертає резервний результат, якщо сталася помилка (таймаут).

**Обґрунтування:**  

Поєднання Timeout + Fallback дозволяє:

- не чекати нескінченно довго,
- повернути контрольований "безпечний" результат, а не необроблений виняток.

### Фрагмент коду

Фрагмент реалізовано в методі `RunScenario3_LongOperationWithTimeoutAndFallback()`:

- основна операція "працює" 3 секунди (`Thread.Sleep(3000)`),
- таймаут встановлено на 1 секунду,
- Timeout кидає `TimeoutRejectedException`,
- Fallback перехоплює помилку і повертає рядок:  
  `Резервний результат: таймаут операції.`

### Очікувана поведінка та логи

- У консолі видно старт довгої операції.
- Через ~1 секунду спрацьовує Timeout:
  - лог `[Timeout] Операція перевищила ліміт ...`
- Потім спрацьовує Fallback:
  - лог `[Fallback] Повертаємо резервний результат...`
- Користувач бачить результат:
  - `Результат для користувача: Резервний результат: таймаут операції.`

## 5. Загальні висновки

1. **Polly** дозволяє описувати відмовостійкість у вигляді **декларативних політик** (Retry, CircuitBreaker, Timeout, Fallback тощо), не захаращуючи бізнес-логіку величезною кількістю `try/catch`.
2. Політики можна **комбінувати** (Wrap), створюючи складні стратегії:
   - повторні спроби для тимчасових збоїв,
   - відсікання постійних помилок через CircuitBreaker,
   - обмеження часу очікування через Timeout,
   - повернення безпечного результату через Fallback.
3. Використання Polly робить .NET-застосунки:
   - **стабільнішими** при роботі з ненадійними зовнішніми ресурсами,
   - **більш керованими** з точки зору обробки помилок,
   - **зручнішими** для користувачів, оскільки помилки або тимчасові проблеми обробляються автоматично.
4. Логування, інтегроване в політики, дозволяє легко відстежувати:
   - як часто виникають помилки,
   - скільки було повторних спроб,
   - коли саме CircuitBreaker переходить у різні стани.

У результаті застосунок стає відмовостійким: він не “падає” через перший збій, а намагається **розумно відновитися** або **повернути контрольований fallback-результат**.
