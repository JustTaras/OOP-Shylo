Відповіді на контрольні питання
1. Поясніть патерн Factory Method. Які проблеми він вирішує?
Патерн Factory Method (Фабричний метод) визначає інтерфейс для створення об'єкта, але дозволяє підкласам вирішувати, який клас інстанціювати.

Проблеми, які вирішує: Він усуває жорстку прив'язку (tight coupling) клієнтського коду до конкретних класів. Якщо вам потрібно додати новий тип ресурсу (наприклад, CloudResourceManager), вам не потрібно змінювати існуючий код, достатньо створити новий клас ресурсу та відповідну йому фабрику.

2. Поясніть патерн Singleton. Коли його доцільно використовувати, а коли варто уникати?
Singleton (Одинак) гарантує, що у класу є лише один екземпляр, і надає глобальну точку доступу до нього.

Коли доцільно використовувати: Коли система потребує рівно одного об'єкта для координації дій. Наприклад: пули з'єднань з БД, менеджери конфігурацій, системи логування або централізовані сервіси (як наш ResourceService).

Коли уникати: Коли він перетворюється на прихований глобальний стан (global state), що робить код важким для тестування (unit testing) і приховує реальні залежності класів один від одного. Також він може стати "вузьким місцем" у багатопотокових додатках, якщо не реалізований коректно.

3. Як ці два патерни можуть працювати разом для створення гнучкої та контрольованої системи?

Singleton виступає в ролі центрального диспетчера (ResourceService), який зберігає стан і надає єдиний інтерфейс для всього застосунку.

Factory Method забезпечує гнучкість створення об'єктів. Singleton не знає, як створювати конкретні ресурси, він лише приймає абстрактну фабрику (ResourceManagerFactory) і просить її виконати роботу.
Ця комбінація дозволяє на льоту змінювати поведінку всієї системи (змінивши фабрику всередині Singleton), при цьому клієнтський код продовжує викликати один і той самий метод service.Manage().

4. Які переваги дає використання абстракцій (інтерфейсів) у поєднанні з Factory Method та Singleton?

Дотримання OCP (Open/Closed Principle): Систему можна розширювати новими типами ресурсів та фабрик, не модифікуючи код Singleton або базової фабрики.

Дотримання DIP (Dependency Inversion Principle): Клієнтський код (метод Main або Singleton) залежить від абстракцій (IResourceManager, ResourceManagerFactory), а не від конкретних реалізацій (FileResourceManager тощо).

Легкість заміни та тестування: Завдяки абстракціям, замість реальної бази даних або мережі, ви можете підставити MockResourceManager для юніт-тестування системи без зміни клієнтського коду.
