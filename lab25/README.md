1. Загальна ідея програми

Було реалізовано консольну систему обробки даних, яка:

Обробляє дані різними алгоритмами (Strategy)

Логує результат через фабрику логерів (Factory Method)

Керує логером через єдиний екземпляр (Singleton)

Сповіщає підписників про обробку даних (Observer)

Патерни взаємодіють між собою, але залишаються слабко зв’язаними.

2. Опис реалізації патернів
2.1 Factory Method
Призначення:

Інкапсулювати створення об’єктів логерів.

Реалізація:
public abstract class LoggerFactory
{
    public abstract ILogger CreateLogger();
}


Конкретні фабрики:

ConsoleLoggerFactory

FileLoggerFactory

Вони створюють відповідні реалізації ILogger.

Результат:

Код не залежить від конкретного типу логера.
Можна легко додати новий логер без зміни існуючої логіки.

2.2 Singleton
Призначення:

Гарантувати існування лише одного об’єкта для керування логуванням.

Реалізація:
public class LoggerManager
{
    private static LoggerManager? _instance;
    private LoggerFactory? _factory;

    private LoggerManager() { }

    public static LoggerManager Instance


Singleton зберігає фабрику та створює логери через неї.

Результат:

Уся система використовує один глобальний менеджер логування.

2.3 Strategy
Призначення:

Дозволити змінювати алгоритм обробки даних під час виконання програми.

Інтерфейс:
public interface IDataProcessorStrategy
{
    string Process(string data);
}


Реалізації:

EncryptDataStrategy

CompressDataStrategy

Контекст:

public class DataContext
{
    private IDataProcessorStrategy _strategy;
}

Результат:

Алгоритм можна змінити через SetStrategy() без зміни коду клієнта.

2.4 Observer
Призначення:

Автоматично сповіщати підписників про завершення обробки даних.

Реалізація:
public class DataPublisher
{
    public event Action<string>? DataProcessed;
}


Спостерігач:

public class ProcessingLoggerObserver


Observer підписується на подію і виконує логування через LoggerManager.

Результат:

Механізм сповіщення працює незалежно від логіки обробки даних.

3. Інтеграція патернів

У програмі патерни взаємодіють наступним чином:

DataContext виконує обробку даних (Strategy).

DataPublisher генерує подію.

ProcessingLoggerObserver реагує на подію.

Observer використовує LoggerManager (Singleton).

LoggerManager створює логер через LoggerFactory (Factory Method).

Таким чином:

Strategy не знає про логування.

Observer не знає конкретного типу логера.

Logger створюється через фабрику.

Singleton забезпечує централізоване керування.

Система є гнучкою та розширюваною.

4. Опис сценаріїв роботи
Сценарій 1 – Повна інтеграція

Використовується ConsoleLogger.

Стратегія: EncryptDataStrategy.

Дані обробляються та виводяться в консоль.

Сценарій 2 – Зміна логера

Фабрика змінюється на FileLoggerFactory.

Логування відбувається у файл.

Архітектура не змінюється.

Сценарій 3 – Зміна стратегії

Стратегія змінюється на CompressDataStrategy.

Алгоритм обробки змінюється під час виконання.

5. Висновок

У ході виконання лабораторної роботи було реалізовано інтегровану систему, що поєднує чотири патерни проєктування:

Factory Method

Singleton

Strategy

Observer

Було продемонстровано їх спільну роботу та можливість динамічної зміни:

типу логера

алгоритму обробки даних

Архітектура відповідає принципам об’єктно-орієнтованого програмування:

інкапсуляція

поліморфізм

слабка зв’язаність

розширюваність

Система компілюється та працює без помилок, що підтверджує коректність інтеграції патернів.
